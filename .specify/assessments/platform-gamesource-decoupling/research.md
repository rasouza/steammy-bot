The intake was raised minutes after this merge. — [source: `git log origin/main`, `specs/003-easy-add-platform/`] (confidence: high)
- **The layout question was explicitly researched and decided 3 days ago — and the decision was *one* module.** Spec 003 research **R7 "File and module layout"**: contracts + runtime + registry + scheduler + factory at `src/modules/platforms/` root, `epic/`/`xbox/` as sub-folders; rationale: "The reference plan explicitly says to keep platform integrations in the existing top-level `platforms` module and **not** create `broadcast/platforms/`. Splitting by concern (api/mapper/repository) is the developer experience the spec's Story 1 measures." The idea at hand reopens R7 with a different split axis (module boundary, not folder). — [source: `specs/003-easy-add-platform/research.md` §R7 on merged PR #28] (confidence: high)
- **The "storefront" vocabulary comes from spec 003 / `docs/platform-integration.md`**, which say "storefront components", "storefront-specific", "per-storefront folder" throughout — this resolves intake unknown #3: the "storefront folders (xbox and epic)" the idea refers to are the merged `src/modules/platforms/{epic,xbox}/` folders, not a pre-existing structure on `main`. — [source: `docs/platform-integration.md` (merged), spec 003 US1] (confidence: high)
- **"GameSource" is a new name**: zero occurrences of `gamesource` (case-insensitive) in `src/`, `docs/`, `specs/`, `README.md`, `AGENTS.md` on the current tree — the rename would land on docs/specs that currently say "storefront" (~everywhere in spec 003 and the integration guide). — [source: repo grep 2026-09-30] (confidence: high)

- Precedent for import-path-only moves in this repo is good: `src/shared/` was retired inside STE-1 (T037–T042) — "Import paths in consuming modules change; no runtime behavior does" (A-010). So the mechanics of moving files are proven; a *module split* additionally changes the DI/module graph, which the shared retirement did not. — [source: spec 003 assumptions A-010; `platforms.module.ts`] (confidence: high)

A split moves/renames import specifiers in those files plus intra-module edges. — [source: `git grep` of module references on merged tree] (confidence: high)
- **Cost of doing nothing**: nothing — the merged design already meets spec 003's acceptance criteria (one lifecycle, no platform branching, send→mark ordering, preserved schedules) and STE-75 remains available for the two other DX levers (migrations, generator). The bot's production behavior is unaffected either way. — [source: spec 003 acceptance criteria; Linear STE-75; ASSUMPTION that no user-facing regression pressure exists] (confidence: medium)
- **External prior art not consulted**: no web sources were fetched. `docs.nestjs.com/custom-providers` and `/techniques/task-scheduling` are cited inside the repo plan but were **auto-refused** here (host not on the allowlist, and the available fetch mechanism cannot pin or expose the connected peer as the URL Trust Policy requires). — [source: `docs/plans/easy_add_platform.md` §4/§6 references; URL Trust Policy] (confidence: high)

## Data & Constraints

- Scale of a comparable change: STE-1 = 44 files / +3010 / −441 in one PR; the merged `src/modules/platforms/` tree is 21 files (incl. specs). A module-boundary split would touch the same file set again plus its 9 external consumers. — [source: `git show d586177 --stat`, `git ls-tree`] (confidence: high)
- **ESM hazards amplify any move**: every relative import carries an explicit `.js`/`/index.js` extension (19 barrels, 70 specifiers); `verbatimModuleSyntax` forces `import type` discipline. Moving files across a module boundary rewrites these everywhere, and `prettier --check` fails on line-ending churn. — [source: AGENTS.md "Changing the toolchain", "Conventions that differ"] (confidence: high)
- **Current module graph direction**: `PlatformsModule → BroadcastModule` (factory injects `BroadcastService`), exports `PLATFORM_REGISTRY` + `PlatformScheduler`. Splitting generic-runtime vs GameSource into two modules must decide who owns the broadcast port and avoid a cycle — the single composition-root comment in `platforms.module.ts` currently holds both halves. — [source: `platforms.module.ts` (merged)] (confidence: high)
- Process constraints: Linear is tracker of record (feature branches need the `STE-x` key); CI gate = prettier → type:check → lint → build → test:cov → test:e2e; STE-1's rules say "Do NOT combine with other plans — separate PRs". — [source: AGENTS.md, STE-1 description] (confidence: high)
- Related open work that could collide: STE-75 (generator would scaffold files into *some* directory layout; unified catalog table would remove the per-platform repository/migration touch point) and STE-74 ("Move the broadcasted flag into its own broadcast-tracking table", blocked-by STE-1) — both touch the same files. — [source: Linear STE-74/STE-75, STE-1 relations] (confidence: high)

## Evidence Against the Idea

- **The DX premise is unmeasured and its validation is still pending.** Spec 003's research (R7) already rejected a re-layout the day before, the merged acceptance criteria are met, and STE-76 — the non-author check that the guide actually delivers the claimed ease — hasn't started. There is no evidence yet that a *module* boundary (vs. the existing *folder* boundary) makes adding a platform any easier: the registration touch points (constants, registry, module provider list, Discord DTO choice) exist in both designs, and the plan explicitly allows the composition root to change (§10). — [source: spec 003 R7, plan §10, Linear STE-76] (confidence: high)
- **Same-day churn over just-landed behavior-preserving work.** STE-1's acceptance required byte-identical message literals, preserved cron timings (A-003), eligibility parity, and send→mark ordering across 44 files; re-splitting those files immediately multiplies regression risk for an unproven DX gain, and STE-1's own rule forbids combining changes into one PR. — [source: spec 003 SCs, STE-1 rules, tasks T028/T029] (confidence: high)
- **Possible overlap/conflict with STE-75**, which already owns "simplify adding new storefront platforms" and attacks two different root causes (per-platform migrations, manual scaffolding). A generator (STE-75) hard-codes a target directory layout — building the generator first, then moving directories, wastes one of the two. Which order to do them is undecided and no relation is recorded between STE-75 and this idea. — [source: Linear STE-75; ASSUMPTION on sequencing cost] (confidence: medium)
- **Benefit accrues to a team that doesn't exist.** Module boundaries primarily pay off with multiple contributors/parallel work; this is a single-maintainer repo where the composition root is edited by design. The added DI wiring (two modules, export/import contracts, possible cycle around `BroadcastService`) is real complexity with no measured offset. — [source: ASSUMPTION (repo has one contributor per git/Linear history: all commits by Rodrigo Souza)] (confidence: medium)
- **No user or production signal.** Nothing in issues, incidents, or the plan indicates the current structure causes bugs or delivery failures post-merge; the concrete bugs (broadcast-before-send, platform branching) were already fixed by STE-1. — [source: Linear STE-1 acceptance criteria, git log; ASSUMPTION] (confidence: medium)
